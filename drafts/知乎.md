# 如何评价 agent-publishing-skills 这个面向 AI Agent 的通用发布技能库？

## 问题

AI Agent 工具（Claude Code、Gemini CLI、Codex 等）的能力边界正在快速扩展，从写代码到改 bug 再到部署运维，几乎覆盖了开发流程的每个环节。但「把项目介绍发到不同技术社区」这个看似简单的任务，目前的 Agent 做得并不好——要么生成千篇一律的文案，要么不了解各平台的内容规范。

agent-publishing-skills 是一个瞄准这个痛点的开源项目，它为 AI Agent 提供了一套「发布技能」——包括规划（planner）、撰写（writer）、适配（adapter）和审查（reviewer）四个环节。

## 分析

### 1. 架构设计的合理性

项目最值得关注的设计选择是将「平台知识」和「执行逻辑」完全拆开：

- **knowledge/** 目录存放 91 个平台的标准化描述（语言、格式、语调、适配要求），每个平台一个 Markdown 文件。这部分是纯数据，不含任何执行代码。这意味着新增平台不需要修改任何技能逻辑——添加一个 Markdown 描述文件即可。
- **skills/** 目录存放四个技能的 Markdown 指令，定义了 planner → writer → adapter → reviewer 的完整工作流。这些技能遵循 JSON Schema 契约，输入输出可验证。

这种分离模式借鉴了「知识库 + 推理引擎」的经典架构，使得系统的两个维度可以独立演化。

### 2. 适配策略的工程务实性

项目没有对所有平台一视同仁地使用统一适配器，而是采用了分级策略：

- 6 个专用适配器（DEV、Zenn、Qiita、Hacker News、Reddit、Product Hunt）处理行为特殊的平台。
- 5 个通用适配器（technical-blog、community-discussion、launch、showcase、social-shortform）覆盖其余 85 个平台。

这种「通用覆盖 + 专用增强」的策略在工程上是务实的——Zenn 的 emoji 排版系统和 Product Hunt 的多字段文案要求确实无法用通用逻辑妥善处理。

### 3. 安全约束的设计

项目内置了四条硬性规则：no-auto-publish（绝不自动发布）、anti-spam（反垃圾检测）、disclosure（透明披露）、factual-accuracy（禁止编造数据）。

这四条规则不是建议而是约束——它们在 schema 和技能执行层面被强制执行。这反映了项目对 AI 生成内容风险的清醒认知：生成错了可以改，但自动发出去就是事故了。

## 方案对比

目前市面上解决类似问题的方案主要有三类：

| 方案 | 代表 | 局限 |
|------|------|------|
| 手工跨平台发布 | Buffer、Hootsuite | 需要人手动编写每个平台的文案 |
| AI 内容生成工具 | Jasper、Copy.ai | 主要面向营销文案，不懂技术社区规范 |
| Agent 自定义提示词 | 各 Agent 原生 | 每个开发者需要自己写平台规则，不可复用 |

agent-publishing-skills 的定位填补了第三类方案的空白——提供一套可复用的、社区维护的平台知识层。

## 局限与风险

客观地说，项目有几个值得注意的局限：

1. **平台知识档案依赖人工维护**：91 个平台的规则变化需要手动更新，缺少自动爬取或监听机制。
2. **草稿质量依赖底层 LLM**：技能本身只是「指导 Agent 做什么」的指令，实际文字生成质量取决于加载技能的 LLM 模型能力。
3. **中文平台的适配深度不足**：CSDN、掘金、知乎、少数派等中文平台目前共用 `adapter-technical-blog` 通用适配器，没有为它们开发专用适配器。
4. **社区贡献门槛**：新增平台需要编写符合规范的 Markdown 知识档案，对非技术社区的不够友好。

## 总结

agent-publishing-skills 解决了一个「看似简单但实际很复杂」的问题——让 AI Agent 理解不同技术平台的内容差异并按规范生成适配稿。它在架构上做了正确的取舍（知识层与逻辑层分离），在工程上做了务实的折中（通用适配器 + 专用适配器），在安全上设置了硬约束（绝不自发行为）。

项目的核心价值不在于生成文字（那是 LLM 的事），而在于提供了一套可复用的平台知识和适配规则——让 Agent 从「我会写」变成「我知道该写成什么样」。
